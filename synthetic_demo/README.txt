49-C SYNTHETIC DATA — FOR SOFTWARE TESTING AND UI DEMOS ONLY

This dataset contains 300 fictional consumer profiles x 5 simulated personalization scenarios = 1,500 rows.
No respondent, advertising outcome, or experiment observation comes from a real person.
All numbers are generated by the included script using seed 49026 and intentionally assumed equations.

The five scenarios are project-defined concepts, not validated experimental manipulations:
L0 generic, L1 contextual/demographic, L2 behavioral, L3 historical, L4 combined/hyperpersonalization.

Predictors marked _pre are simulated characteristics assumed known before ad exposure.
Privacy/relevance quadrants ('simulated_segment') are generated labels, not validated market segments.
Disclosure is randomized in each simulated exposure and reduces the simulated discomfort formula by 0.35.
Outputs are simulated 1–7 discomfort, relevance, and engagement-intention ratings.
High discomfort is a simulated indicator for generated discomfort >= 5.
Each synthetic consumer has five rows. 'split' is assigned by consumer ID, ensuring all five rows
of a consumer are in the SAME partition (240 train consumers; 60 test consumers).

CRITICAL: The generating equations deliberately encode a relationship between personalization
intensity, pre-exposure traits and outcomes. A model may learn these artificial equations and
achieve impressive metrics, but this is NOT validation on consumers and MUST NOT support
empirical research findings, individual real-user scoring or L0–L4 recommendations in production.
The real project's threshold_engine.py must still return 'insufficient_evidence' on empirical data.

Useful applications: demonstration UI, schema validation, model interface unit tests,
train/test leakage tests, stress tests, and comparison of software implementations.
Do not merge synthetic rows with real survey records for model validation.
Use a prominent 'SIMULATED DEMO' label in any user-facing interface.
